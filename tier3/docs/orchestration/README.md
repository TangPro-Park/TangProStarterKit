# docs/orchestration/ — 멀티에이전트 오케스트레이션 (Tier 3)

> 1~3인 + AI 협업이 *여러 에이전트*로 확장될 때, "여러 에이전트를 어떻게 동시에 굴리고·통신시키고·검증하는가" 를 다루는 모듈.
>
> 본 모듈은 METHODOLOGY Part II 원리 6 (**병행 가능성 우선**) 의 실천편이다. 한 사람이 직렬로 다 못 하는 일을 *여러 에이전트로 펼치되, 무질서하게 펼치지 않는* 표준을 제시한다.

---

## 언제 도입하나

- 단일 에이전트(한 세션·한 대화) 로 처리하기엔 *작업이 많거나·서로 다른 전문성*이 필요할 때
- 같은 작업을 *수십 건 병렬*로 돌려야 할 때 (자료 처리·배치 추출)
- 한 결과물을 *적대적으로 검증*해야 신뢰가 서는 곳 (재무 판단·규제 응답)

> Tier 1·2 만으로 충분한 단계라면 본 모듈은 미적용. 1인 단일 세션이면 오버헤드만 늘어난다.

---

## ★ 3 실행 모드 구분표

세 가지는 *경쟁이 아니라 층*이다. 보통 ①을 먼저 깔고, 그 위에서 ② 또는 ③을 고른다.

| | 🛠 하네스 구성 | 👥 Agent Teams | 🟣 Dynamic Workflows |
|---|---|---|---|
| **층** | 설계 층 (각 에이전트의 *실행환경*) | 협업·관찰 층 | 대량 병렬·검증 층 |
| **핵심** | 도구·skill·프롬프트·진입점 큐레이션 | 에이전트 간 메시지·관찰 | 스크립트로 수십 에이전트 결정적 제어 |
| **통신** | (해당 없음 — 환경만 구성) | 있음 (SendMessage) | 없음 / 단계 산출물로 전달 |
| **관찰** | — | tmux 분할 pane 으로 실시간 | 로그·구조화 출력 |
| **규모** | 1 에이전트당 1 환경 | 소수 (2~6) | 대량 (수십~수백) |
| **제어흐름** | — | 사람·orchestrator 가 유도 | 코드 (pipeline / parallel) |
| **언제** | *환경을 짜야 할 때* (항상 먼저) | *에이전트끼리 메시지가 필요할 때* | *대량 독립 작업 + 결정적 제어 + 엄격 검증* |
| **문서** | `harness_engineering.md` | `agent_teams.md` | `dynamic_workflows.md` |

## "언제 무엇을 쓰나" 의사결정 가이드

```
시작
 │
 ├─ 에이전트의 실행환경(도구·skill·프롬프트)부터 짜야 하나?
 │      └─ 예 → 🛠 하네스 구성  (harness_engineering.md)  ※ 거의 항상 선행
 │
 ├─ 에이전트끼리 서로 메시지를 주고받아야 하나? (역할 분담·중간 합의)
 │      └─ 예 → 👥 Agent Teams  (agent_teams.md)
 │
 ├─ 같은 작업을 수십 건 병렬 + 결정적 제어흐름 + 엄격 검증이 필요한가?
 │      └─ 예 → 🟣 Dynamic Workflows  (dynamic_workflows.md)
 │
 └─ 위 어디에도 해당 없음 → 멀티에이전트 불필요. 단일 세션으로.
```

분기 한 줄 요약 — **서로 메시지가 필요하면 Teams, 대량·독립·검증이면 Workflows, 그 전에 환경은 하네스.**
