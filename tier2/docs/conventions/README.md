# docs/conventions/ — 코드·데이터·문서 표준

> 프로젝트 전체에 강제되는 *표준* . SPEC 보다 권위 약하지만 PR 마다 재논의 막는 가드레일.

---

## 작성 규칙

1. 파일명: `<주제>.md` (예: `naming.md` / `api_design.md` / `data_format.md`)
2. 한 파일 = 한 표준 영역
3. *왜 이 표준인가* 1단락 명시 — 표준의 권위는 이유에서 온다
4. 대안(고려했지만 채택 안 한 옵션) 1단락 — 미래 변경 검토 시 필요
5. 위반 시 어떤 일이 일어나는가 — 구체적 사례

---

## 권장 초기 파일

| 파일 | 무엇 |
|---|---|
| `naming.md` | 변수·함수·파일·타입 네이밍 규칙 |
| `error_handling.md` | 예외 처리·에러 메시지 표준 |
| `api_design.md` | 외부 API 인터페이스 표준 (REST/GraphQL/gRPC 등) |
| `data_format.md` | 데이터 스키마·직렬화·마이그레이션 표준 |
| `commit_messages.md` | git commit 메시지 형식 |

---

## 한 파일 표준 골격

```markdown
# <표준 주제>

> 1줄 정의 — 이 표준이 다루는 범위.

## 1. 왜 이 표준인가
(이유 1단락)

## 2. 규칙
- (규칙 1)
- (규칙 2)

## 3. 예시
✅ 좋은 예
❌ 나쁜 예

## 4. 고려했지만 채택하지 않은 대안
- 옵션 X — 사유

## 5. 위반 시
(구체적 사례)

## 6. 변경 이력
```

---

## 운영 팁

- *코드와 어긋나는 표준* 은 표준이 아니다 → 발견 즉시 코드 수정 또는 표준 수정
- 새 표준 도입은 *PR 단위 토론 후* 본 디렉토리 진입
- 표준 위반이 PR 에서 3건+ 누적되면 lint/CI 룰로 자동화 검토
